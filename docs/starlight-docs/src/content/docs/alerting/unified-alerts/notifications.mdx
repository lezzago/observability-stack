Creating a rule tells the stack *when* to alert. A **notification channel** tells it *where* to send the alert — Slack, email, PagerDuty, or a custom webhook. The two rule types deliver notifications through different mechanisms, so set them up separately:

| Rule type | Notifications go through | Configured in |
|---|---|---|
| **Metric rule** (Prometheus/PromQL) | **Alertmanager** receivers + routing tree | `docker-compose/alertmanager/alertmanager.template.yml` |
| **Log rule** (OpenSearch/PPL) | **Trigger actions** using OpenSearch **Notifications** channels | OpenSearch Dashboards → Notifications, then attached in the rule |

<Aside type="note" title="Alerts are stored even without a channel">
Out of the box, every firing metric alert is indexed into the `alertmanager-alerts` OpenSearch index by the default receiver, so you have a searchable history before you wire up any external channel. External delivery (Slack/email/PagerDuty) is what you add on top.
</Aside>

## Metric-rule notifications (Alertmanager)

Metric alerts from the Cortex ruler are sent to **Alertmanager**, which groups, deduplicates, and routes them to **receivers**. The stack ships a working config at:

```
docker-compose/alertmanager/alertmanager.template.yml
```

It defines a routing tree, a default `opensearch-webhook` receiver that indexes alerts into OpenSearch, and **placeholder receivers for Slack, email, and PagerDuty** that you fill in with real credentials. Credentials for the OpenSearch receiver are injected from `.env` (`OPENSEARCH_USER` / `OPENSEARCH_PASSWORD`) at container startup.

### Add a Slack receiver

The template already includes a `dummy-slack` receiver — replace the placeholder `api_url` with a real Slack [incoming webhook](https://api.slack.com/messaging/webhooks) URL:

```yaml
receivers:
  - name: 'slack-notifications'
    slack_configs:
      - api_url: 'https://hooks.slack.com/services/<workspace>/<channel>/<token>'
        channel: '#alerts'
        send_resolved: true
        title: '[{{ .Status | toUpper }}] {{ .CommonLabels.alertname }}'
        text: |
          {{ range .Alerts }}
          *Severity:* {{ .Labels.severity }}
          *Service:* {{ .Labels.service_name }}
          *Summary:* {{ .Annotations.summary }}
          {{ end }}
```

Then add a route so matching alerts reach it. Routes are evaluated top-down, first match wins:

```yaml
route:
  receiver: 'opensearch-webhook'   # default catch-all
  routes:
    - match:
        severity: critical
      receiver: 'slack-notifications'
```

### Add an email receiver

```yaml
receivers:
  - name: 'email-notifications'
    email_configs:
      - to: 'oncall@example.com'
        from: 'alertmanager@observability-stack.local'
        smarthost: 'smtp.example.com:587'
        auth_username: 'alertmanager@example.com'
        auth_password: 'CHANGE_ME'
        require_tls: true
        send_resolved: true
```

### Add a PagerDuty receiver

```yaml
receivers:
  - name: 'pagerduty-notifications'
    pagerduty_configs:
      - routing_key: '<your-integration-routing-key>'
        send_resolved: true
        severity: '{{ .CommonLabels.severity }}'
        description: '{{ .CommonAnnotations.summary }}'
```

### Apply and validate

1. Edit `docker-compose/alertmanager/alertmanager.template.yml`.
2. Validate the config before restarting:

   ```bash
   docker exec alertmanager amtool check-config /tmp/alertmanager.yml
   ```

3. Restart Alertmanager to pick up the change:

   ```bash
   docker compose restart alertmanager
   ```

4. Alertmanager's own UI is available at `http://localhost:9093` — use it to see active alerts, grouping, and any **silences**.

<Aside type="tip" title="Suppressing noise">
To stop a noisy alert without deleting its rule, use an Alertmanager **silence** (in the `:9093` UI or via `amtool silence add`), or route it to the built-in `null` receiver. The shipped config also uses **inhibition rules** to suppress warnings when a critical alert fires for the same service.
</Aside>

For the full receiver reference (webhook, OpsGenie, VictorOps, and more), see the [Alertmanager configuration docs](https://prometheus.io/docs/alerting/latest/configuration/#receiver).

## Log-rule notifications (trigger actions)

Log rules notify through **actions** attached to their triggers, using the OpenSearch **Notifications** plugin. The flow is:

1. In OpenSearch Dashboards, open **Notifications** and create a **channel** (Slack, Chime, email/SES, or a custom webhook).
2. When you [create or edit a log rule](/docs/alerting/unified-alerts/create-rules/#log-rule-ppl), open the trigger's **Notification actions** section and choose **Add another action**.
3. Select the channel and, optionally, customize the message with the trigger's context.

Because log-rule actions fire per trigger, you can send different severities to different channels from the same rule.

For channel setup details, see the [OpenSearch Notifications documentation](https://docs.opensearch.org/latest/observing-your-data/notifications/index/).

## Verify delivery

After wiring a channel, confirm it works end to end:

- **Metric rules** — check the target channel received a test alert, and cross-check `http://localhost:9093` for the alert in Alertmanager. Every alert is also queryable in OpenSearch:

  ```bash
  curl -sk -u admin:$OPENSEARCH_PASSWORD \
    "https://localhost:9200/alertmanager-alerts/_search?pretty"
  ```

- **Log rules** — trigger the condition (or use **Run preview** on the rule) and confirm the notification arrives; the alert also appears in [Explore Alerts](/docs/alerting/unified-alerts/explore-alerts/).

If nothing arrives, see the [alert troubleshooting checklist](/docs/alerting/unified-alerts/explore-alerts/#alert-isnt-firing).
